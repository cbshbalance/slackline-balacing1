# v22 실물 트윈·엔코더·영점 수정 인계

작성: 2026-09-06. 이 문서를 새 프로젝트 세션의 시작 자료로 사용한다.

## 1. 바로 이어서 할 일

사용자는 한국어로 소통한다. 이틀간 하드웨어/펌웨어 문제를 실험했으며 이제 **측정 → 단일 접기 → 증분접기**로 진행하려 한다.

가장 최근 요청은 다음 순서였다.

1. 허리 왕복 테스트의 고정 ±10°/2초를 **진폭·간격 입력 방식**으로 변경. ±20°/1초도 시험하고 싶음.
2. **영점은 명시적인 0점 설정에서만 변경**하고, 토크 ON·실험 시작·수동 명령에서는 재설정하지 않도록 전체 관련 경로 수정.

두 수정본을 만들었지만, **2단계 통합 수정본은 실제 프로젝트에 적용되지 않았고 보드 빌드·업로드·구동도 확인하지 못했다.** 새 세션에서는 수정본 검토와 프로젝트 반영부터 이어가야 한다. 처음부터 하드웨어 진단을 다시 시작하지 말 것.

인계 직전 실제 파일을 읽어 확인한 상태:

- 프로젝트 앱에는 **진폭·간격 입력이 있는 1단계 버전이 이미 설치돼 있다.**
- 그 앱은 아직 `h\nk`를 보내고, 구형 “토크 ON” 문구로 준비를 확인한다. 영점 문제는 남아 있다.
- 프로젝트의 `v22_logger/firmware/v22_raw/v22_raw.ino`는 아직 **기존 v3, SPI 1MHz**이다.
- 사용자가 보드에 올려 정상 트윈을 확인한 것은 이 대화의 outputs에서 받은 **별도 v22 raw v3 SPI 100kHz 버전**이다. **프로젝트 원본과 보드에 업로드한 파일이 다르다.**
- GitHub에 이 대화의 변경을 커밋·푸시한 적은 없다.

## 3. 최신 산출물 — 무엇을 사용할지

### A. 입력 옵션만 추가한 1단계 (프로젝트에 설치된 것으로 확인)

```text
OUT\v22_twin_options.zip
OUT\v22_twin_options\static\lg_twin_test.js
```

- 진폭: 정수 1~40°, 기본 10°.
- 전환 간격: 0.5~10초, 기본 2초.
- 진폭 20/간격 1은 **+20°와 −20°를 1초마다** 명령한다. 양 끝 차이는 40°, 한 왕복은 2초.
- 실행 중 입력 비활성화, 정지 후 변경.
- 이 단계는 기존 `k` 영점 재설정 동작을 유지했다. 완성된 영점 수정본으로 혼동하지 말 것.

### B. 최신 통합 수정본 (검토·반영·보드 확인이 다음 작업)

```text
OUT\v22_zero_fix.zip
OUT\v22_zero_fix\firmware\v22_raw_zero_fix\v22_raw_zero_fix.ino
OUT\v22_zero_fix\static\lg_twin_test.js
OUT\v22_zero_fix\static\logger.html
OUT\v22_zero_fix\static\lab.html
OUT\v22_zero_fix\commands.json

OUT\v22_zero_fix\사용방법.txt
OUT\v22_zero_fix\apply.ps1
OUT\v22_zero_fix\install-map.json
```

통합본의 표시 버전은 **v22_raw v3.2**이다. 프로젝트에 정식 반영·릴리스됐다는 뜻은 아니다.

반영 대상은 다음 5개 파일이다. 새 세션에서는 차이를 확인해 직접 반영하면 된다.

| 제공 파일 | 프로젝트 대상 |
|---|---|
| `static/lg_twin_test.js` | `v22_logger/static/lg_twin_test.js` |
| `static/logger.html` | `v22_logger/static/logger.html` |
| `static/lab.html` | `v22_logger/static/lab.html` |
| `commands.json` | `v22_logger/commands.json` |
| `firmware/v22_raw_zero_fix/v22_raw_zero_fix.ino` | `v22_logger/firmware/v22_raw/v22_raw.ino` |

위 표의 제공 파일명/대상 경로가 핵심이며, 실제 코드는 한국어 UI이다. HTML은 스크립트 캐시 버전을 `v=3`으로 바꾼 것뿐이다. 새 세션에서 다른 HTML 수정이 있으면 파일 전체 덮어쓰기 대신 해당 부분만 합친다.

`apply.ps1`은 원본 해시를 확인하고 `v22_logger/zero-fix-backup-*`에 백업한 뒤 위 5개 파일을 복사한다. 보드에 자동 업로드하지 않는다. 기존 설치본 또는 1단계 파일을 허용하며 다른 최신 수정이 있으면 중단한다.

### C. 확인된 기존 기준 펌웨어

```text
OUT\v22_raw_spi100k\v22_raw_spi100k.ino
OUT\v22_raw_spi100k.zip
```

프로젝트의 기존 v22 raw v3에서 SPISettings 두 곳만 1MHz→100kHz로 바꾸고 헤더 문구를 추가했다. 사용자가 v22 앱 트윈과 토크 ON이 잘 된다고 확인한 버전이다. 영점/모터 처리 문제는 그대로 남아 있었다.

### D. 혼동하면 안 되는 과거 산출물

`OUT\v22_raw\v22_raw.ino`는 이전에 만든 **v3.1 SPI 오류 검증·잘못된 샘플 유지용 실험 수정본**이다. 사용자는 이후 최소 펌웨어 검증을 선택했다. 이번 통합 수정의 기반은 이 v3.1이 아니라 **원래 v3 + SPI100kHz**이다.

`OUT\v22_twin_test.zip`은 입력 옵션이 없는 최초 ±10°/2초 UI이다. 최신으로 사용하지 말 것.

## 4. 로봇과 통신

- 보드: OpenCR. 시리얼 모니터는 COM9/115200으로 사용했음. 현재 포트는 새 세션에서 확인.
- 외부 엔코더: AS5047P 2개, 파이 φ / 앵클.
- SPI: mode 1, MSB first, CS 파이 D10 / 앵클 D9.
- 모터: 프로젝트 문서상 **DYNAMIXEL XM430-W210-R**, 4핀 RS-485. W350로 잘못 안내한 과거가 있으므로 모델 혼동 금지.
- DXL: Serial3, 방향핀84, ID1, Protocol2. 모터 통신속도와 SPI 클록, PC USB 시리얼 속도는 서로 다르다.
- 이전 모터는 1Mbps로 읽혔다. 새 모터는 `r` 검색 후 **57600bps**로 읽혔다.
- 모터 엔코더의 각도가 허리/델타 δ이다. 새 모터를 케이블만 연결하고 축을 안 움직인 테스트에서 값이 고정된 것은 정상이었다.
- 로봇은 매달려 있고 사용자가 손으로 몸체를 움직이며 시험했다. 몸체에 테이프로 붙인 배선도 같이 움직이며 손이 닿는 조건이다.
- 기존 외부 배선은 40cm 점퍼선 세 개를 납땜해 약1.2m로 만든 구조. 전체 실드선 재제작은 논의했지만 완료됐다는 보고는 없다.
- 자세 정의: φ, ank를 읽고 `alpha=ank-phi`, `theta=alpha+delta`, `beta=alpha+P2R*delta`. 단순히 모터 각도=화면 상체의 절대각은 아니다.
- 매달림/직립 표시에는 fphi/fank 또는 앱 오프셋이 관여한다. 앵클 +180 변환은 과거 필요했지만 중복 적용하지 말 것.

## 5. 실제로 한 하드웨어 조치와 해석

사용자가 정리한 조치:

1. 모터 케이블 4가닥을 새 케이블로 재납땜 연결.
2. 배터리 충전. 충전 전 전압 측정은 약10.5V였으나 부하 상태 전압은 확인하지 못함.
3. USB 연결부에 길이 여유를 주고 테이핑.
4. 헐거웠던 보드 3.3V 핀을 구부려 다시 끼움. 이는 임시 접촉 보강이며 단자 자체의 정식 교체는 미확인.
5. D9 핀 통전 확인 후 다시 꽂음.
6. 외부 SPI 요청 클록을 1MHz에서100kHz로 낮춤.

기존 모터 케이블은 측정봉을 고정한 통전 시험에서 납땜 부근을 만질 때 통전음이 끊겼다 이어지는 징후가 있었다. 이것은 해당 접합부/인접 전선 접촉 불량의 직접 단서다.

새 케이블에 이전 모터를 연결한 기록에서는 **1083회 모두 정상 응답하고 실제 각도도 크게 변했다.** 이전 모터 자체가 고장이라고 결론 내릴 근거는 크게 약해졌다.

모터가 테스트 중 떨어져 분리됐다가 사용자가 다시 꽂은 기록도 있다. 그때의 긴 무응답 구간을 자발적인 모터 고장으로 오인하지 말 것.

외부 엔코더 오류는 최소 원값 펌웨어에서도 재현됐다. 당시 기록 중 한쪽 `0xFFFF`, 한쪽 `0`, 두 채널 동시 `0`이 있었다. 0 또는16383이라는 이유만으로 오류로 분류하지 말고 전후 연속성을 본다. 예: `171 → 0 → 16226`은 정상 회전 경계 통과일 수 있다. `2361 → 0 → 0 → 2356`은 해당 주변 동작에서 비정상이다.

1MHz v22 최소 확인에서 앵클 0 점프가 남았으나 **100kHz 변경 뒤 975개+1080개(총2055개, 약103초) 원값 기록이 정상**이었다. 이어 v22 트윈·토크 ON도 정상이라고 사용자가 확인했다. 긴 배선에서 클록 저하가 안정성에 기여했을 가능성이 높지만 여러 하드웨어 조치가 겹쳤으므로 모든 문제를100kHz 하나로 단정하지 않는다.

## 6. 왕복 테스트에서 새로 확인한 지연·영점 문제

사용자 관찰:

- 시작 버튼을 누르면 화면에는 명령이 나가는데 몇 번 반복된 뒤에야 움직임.
- 처음 살짝 움직이고 이후 잘 왕복.
- 똑바로 매달린 상태 기준 ±10°를 기대했는데 0~20°처럼 치우쳐 보임.
- 트윈 각도도 이상해짐.
- 과거 증분접기 시작에도 비슷한 지연 느낌이 있었음.
- **추가 테스트에서는 지연 없이 시작하기도 했음.** 항상 재현되는8초 지연으로 취급하지 말 것.

실제 저장 로그를 찾아 확인했다:

```text
PROJECT\v22_logger\logs\20260906_151716_auto.raw.txt
PROJECT\v22_logger\logs\20260906_151716_auto.csv
PROJECT\v22_logger\logs\20260906_151716_auto.events.csv
OUT\twin_start_review.csv
```

여기서 PROJECT는 2절 실제 프로젝트 경로이다. raw 로그는 약15MB. 지난날의 다른 로그는400MB 이상이므로 불필요하게 전체 출력하지 말 것.

핵심 증거:

- 첫 `MOVE,+10`은 장치 시각1497925ms.
- 처음4회의 `+10,-10,+10,-10` 동안 raw 약3892 유지.
- 5번째 명령 후, 최초 MOVE에서 약 **8.16초** 지나 raw가 움직이기 시작.
- 명령 간격은 실제 펌웨어 이벤트에서도 약2초. UI 타이머만 늦었던 것은 아님.
- `1508005ms MOVE,-10` 직전 raw4000/delta약+9.49° → 직후 raw4000/delta약+0.09°. 물리 위치는 그대로인데 기준이 이동.
- `1512101ms MOVE,-10` 부근에도 기준이 재설정됨.
- 계산상 home은 약3891~3892 →3999 →4104로 이동. 최초보다 약18.6~18.7° 이동한 기준으로 왕복하게 됨.
- `1510088ms`에 `dxl_raw=16842240`, `delta=1479923.37°`, `err=0`인 명백한 이상값1개. β/각속도/트윈까지 전달됨.

**지연의 직접 원인은 아직 입증하지 못했다.** 위치만 기록돼 있고, 실패한 최초 토크/목표 레지스터의 실제 응답 상태는 당시 로그에 충분히 남지 않았다. “토크ON 실패였음” 또는 “라이브러리 패킷 문제였음”을 확정 사실로 말하지 말 것. 확인된 것은 명령 처리와 실제 움직임의 차이 및 잘못된 소프트웨어 처리다.

기존 코드의 확실한 문제:

- `getTorqueEnableStat()` false를 진짜OFF로만 취급. 읽기 실패도 false가 될 수 있는데 구분하지 않음.
- 수동 숫자 명령의 해당 분기에서 `home_tick = getPresentPosition()`을 실행. `g`도 OFF 판정 시 영점을 다시 잡음.
- `k`는 매번 영점을 재설정하고, 토크 쓰기 성공 여부와 무관하게 “토크 ON” 문구 출력.
- 최초 왕복 앱은 이 문구를 준비 완료로 믿었음. **이 부분은 이번 대화에서 만든 앱의 오류이기도 하다.**
- `writeGoal()` 실패를 카운트만 하고 MOVE/FOLD 이벤트와 제어 진행은 계속함.
- `readDelta()`는 위치값0만 실패로 취급하고 수신 길이/오류를 충분히 확인하지 않음. 반대로 정상 raw0도 실패로 오인 가능.

## 7. 통합 수정본의 구체적인 동작

### 영점

- `home_tick`은 int32, `home_valid`를 별도 관리.
- 시작 시 자동으로 위치를 읽어 영점으로 삼지 않는다. 리셋하면 미설정 상태.
- **실행 중 home_tick 대입은 z 한 곳에만 존재.**
- z에서 두 SPI 프레임과 모터 위치가 모두 정상이어야 기존 영점을 갱신한다. 실패 시 기존 영점 모두 보존.
- 외부 센서의 기존2단계 z 절차 유지. 사용자가 z를 누른 각 단계는 명시적인 영점 설정으로 간주.
- EEPROM 영점 저장은 추가하지 않았음. 업로드·보드 리셋 후 z 필요.
- k/g/숫자 명령/토크복구/왕복준비에서 영점 유지.

### 모터 동작

- raw read: 요청 길이(1 또는4바이트), library error, packet error 확인.
- 위치132번4바이트를 명시적으로 조립. 확장 위치 범위 밖 값은 거부.
- 토크64번 읽기 실패는 UNKNOWN/실패로 처리. OFF로 바꾸어 해석하지 않음.
- 목표116번과 토크 쓰기 응답 및 readback 확인.
- k/g는 현재 위치를 목표로 잡아 유지하되 측정 영점은 그대로.
- 목표 쓰기 실패 시 MOVE/FOLD 성공 이벤트를 내보내지 않고 실험 진행 중단.
- 실제 이동 완료나 물리적 응답 지연까지 해결했다고 주장할 수는 없다. write/readback 확인과 물리적 도착은 다른 단계다.
- SPI100kHz 유지. 원래 CSV 열 순서 유지.
- 초기 모드/설정 쓰기 오류도 기존의 무조건 OK 표시 대신 실패 처리.

### 왕복 앱

- 명령 `h\ntprep <요청번호>`를 보냄.
- 펌웨어가 현재 raw를 읽고 토크를 확인한 뒤 `# TWIN_READY <요청번호> center=<delta> limit=<DELTA_LIM>` 응답.
- 요청번호가 일치하고 최신 데이터가 있어야 시작. 기존 “토크 ON” 문구는 더 이상 준비 완료로 인정하지 않음.
- 시작 delta를 테스트 중심으로 보관. 측정 영점은 유지.
- 예: 시작 delta+5°, 진폭20° → 목표+25° /−15°.
- 숫자 명령이 소수 목표를 처리하도록 펌웨어도 변경.
- 시작 중심±진폭이 실제 dlim을 넘으면 거부. 자동 잘라내기 없음.
- 반복 정지: 반복 종료, 마지막 목표 유지. 비상: x 토크OFF.
- 다른 수동 명령/데이터 소스 교체/통신 끊김/측정값 중단/페이지 이탈 시 취소. 재연결 자동 재시작 없음.
- 통신 자체가 끊긴 경우 정지 명령 전달을 보장하지 못하며 마지막 목표가 남을 수 있음.

## 10. 사용자와 협업 시 지킬 점

- 사용자는 “가능성이 있다/확정할 수 없다”만 반복하고 원인 순위를 매번 뒤집는 답변에 매우 답답해했다. **확인된 사실, 근거 있는 추정, 아직 모르는 부분을 분리하고 다음 조치를 명확히 제시할 것.**
- 앞선 대화에서 배터리, 모터, 배선, SPI를 너무 빨리 주원인으로 단정했다 번복한 적이 많다. 이를 반복하지 말 것.
- 사용자는 문제 감추기나 진단 기능 추가 자체보다 **기본 기능이 제대로 작동하는 코드**를 원한다. 검증을 실패 처리와 연결하고 원인을 모르면 그렇게 명확히 말할 것.
- “바로 시작하면 정상”, “토크ON 문구가 나오니 성공”, “플래그0이니 정상”, “초기원값0이니 읽기 실패” 같은 잘못된 등치를 피한다.
- 추가 정보가 필요하면 이미 저장된 코드·로그부터 읽는다. 사용자가 이미 설명한 모터 교체/배터리/분리 상황을 다시 묻지 말 것.
- 실제 모터는 사용자의 실험 장치이다. 새 프로젝트 세션에서 권한이 생겼다는 이유만으로 테스트용 운동 명령을 임의로 보내지 말 것. 이번 요청은 코드 반영과 인계이며, 이전 작업도 모터를 직접 구동하지 않았다.
- 사용자가 승인한 코드 작업은 불필요한 재확인 없이 완료한다. 완료/검증 범위/미적용 상태는 정확히 말한다.

## 11. 인계 직후 추가 발견: ±20° / 0.5초에서 불규칙한 왕복

사용자가 “0.5초 간격20도에서 불규칙하게 접는다”고 추가로 보고했고, 원본 로그의 최신 구간을 분석했다. **이 결과를 다음 작업 우선순위에 반영할 것.**

확인된 현재 설치 상태는 여전히 1단계 입력 옵션 앱(`h\nk` 사용)이다. 영점 수정 통합본이 설치됐다고 가정하지 않는다.

로그: 같은 `20260906_151716_auto.raw.txt`의 장치 시각 **9717700~9732179ms**. 파일은 계속 커져 당시 약86MB였다. 마지막4MB를 읽어 분석했다.

- ±20° MOVE 이벤트27개, 연속 명령 간격26개.
- 설정은500ms인데 **실제 펌웨어 MOVE 간격은281~747ms**.
- 간격 일부: `458, 473, 699, 490, 468, 420, 656, 573, 560, 383, 670, 464, 593, 518, 747, 419, 625, 281, ...` ms.
- 해당 구간 D행1448개의 시각 간격은 **모두10ms**였다.
- 마지막 명령을 제외한26회 모두 다음 반대 명령 전에 목표각±2° 이내로 도착했다.
- 첫 움직임은122ms, 이후 대체로175~190ms에 목표±2°로 도착했다. 즉 이 기록에서500ms 자체가 모터에 너무 짧아서 도착 못한 것은 아니다.
- 실제 양 끝은 대략 −19~+19°. 추정 home은 약3890으로 유지됐다. 이번 불규칙함은 앞선 영점 이동 현상과 다르다.

판단:

**이 테스트의 주된 불규칙함은 실제 명령 처리 간격이 흔들린 것이다.** 현재 반복은 브라우저 setInterval → WebSocket → Python 서버 → USB/펌웨어 순서로 개별 명령을 보내므로 PC 측 타이밍/전달 지연 영향을 받는다. 정확히 어느 PC 처리 구간이 지연을 만들었는지는 아직 분리 측정하지 않았다. 단순히 “모터가 느림”으로 설명하지 말 것.

후속 구현 권장:

- 반복의 진폭·간격·시작/정지는 앱에서 입력하되 **반복 스케줄 자체는 OpenCR 펌웨어의 비차단 타이머로 관리**한다.
- 영점 수정본의 고정 측정 영점과 별도 테스트 중심 설계를 유지한다.
- 브라우저가500ms마다 각도 명령을 보내는 구조에서 벗어난다.
- 연결/화면 이탈 시 무한 왕복이 남지 않도록 종료 명령과 제한시간/heartbeat 등 종료 정책도 함께 설계한다. 기존에 보장한 정지 동작이 약해지면 안 된다.
- 새 통합본은 아직 tprep 후 앱이 목표를 반복 전송하는 구조다. **이번 타이밍 개선은 만들어 둔 v22_zero_fix에 아직 포함되지 않았다.**
- 과거 최초8.16초 무동작의 직접 원인은 여전히 미확정이며, 이번500ms 주기 흔들림과 같은 원인으로 단정하지 않는다.
